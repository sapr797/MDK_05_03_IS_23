## 2. Теоретическая справка

### 2.1. Стратегия тестирования в Scrum

**Стратегия тестирования** — это документ (или подход), определяющий:

| Компонент | Описание |
|-----------|----------|
| **Цели тестирования** | Что мы хотим достичь тестированием |
| **Уровни тестирования** | Какие уровни будут выполняться (Unit, Integration, System, UAT) |
| **Типы тестирования** | Функциональное, нагрузочное, безопасность и т.д. |
| **Подходы и техники** | Какие техники тест-дизайна используются |
| **Роли и ответственность** | Кто что делает |
| **Инструменты** | Какие инструменты используются |
| **Метрики** | Как измеряем качество |
| **Критерии готовности (DoD)** | Когда задача считается готовой |
| **Управление дефектами** | Процесс работы с багами |

### 2.2. Уровни тестирования в Agile
┌─────────────────────────────────────────────────────────────┐
│ Спринт (1-4 недели) │
├─────────────────────────────────────────────────────────────┤
│ 1. Модульное тестирование (Unit Tests) ← Разработчики │
│ 2. Интеграционное тестирование ← Разработчики │
│ 3. API-тестирование ← QA + Dev │
│ 4. Функциональное тестирование ← QA (ручное) │
│ 5. Регрессионное тестирование ← QA (авто + руч)│
│ 6. Исследовательское тестирование ← QA │
│ 7. Приёмочное тестирование (UAT) ← PO + Заказчик │
└─────────────────────────────────────────────────────────────┘

### 2.3. Определение готовности (DoD)

**Definition of Done (DoD)** — это список критериев, которым должна соответствовать задача, чтобы считаться готовой.

**Типичный DoD для юзер-стори:**

| Критерий | Ответственный |
|----------|---------------|
| ✅ Код написан и проходит ревью | Разработчик |
| ✅ Написаны Unit-тесты (покрытие ≥ 80%) | Разработчик |
| ✅ Написаны интеграционные тесты | QA + Dev |
| ✅ Выполнено ручное тестирование | QA |
| ✅ Регрессия пройдена | QA |
| ✅ Баги исправлены | Команда |
| ✅ Приёмочные критерии выполнены | QA + PO |

## 5. Пример выполнения (Вариант 1)

### 5.1. Исходные данные

**Проект:** Интернет-магазин электроники
**Команда:** 1 PO, 1 SM, 3 разработчика, 1 QA
**Спринт:** 2 недели

### 5.2. Анализ проекта

**Основные риски:**

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| Сбой платёжной системы | Средняя | Критическое | Автоматизированные тесты интеграции |
| Ошибка в расчёте корзины | Высокая | Критическое | Модульное тестирование + ручное |
| Проблемы с доставкой | Средняя | Высокое | Интеграционное тестирование |
| Безопасность платежей | Низкая | Критическое | Security тестирование |

**Критические модули:**
1. **Оплата** — любой баг здесь → потеря прибыли.
2. **Корзина** — неправильный расчёт → конфликты с клиентами.
3. **Регистрация/вход** — потеря пользователей.

### 5.3. Роли и ответственность

| Роль | Имя | Ответственность |
|------|-----|-----------------|
| PO | Анна | Приоритеты, приёмочные критерии |
| SM | Иван | Процессы, блокеры |
| Разработчик 1 | Петр | Модуль каталога, Unit-тесты |
| Разработчик 2 | Ольга | Модуль корзины и заказа |
| Разработчик 3 | Сергей | Модуль оплаты и ЛК, Unit-тесты |
| QA | Мария | Все виды тестирования, автоматизация |

**Подключение QA:**
- ✅ Анализ юзер-стори (День 1-2).
- ✅ Написание тест-кейсов и чек-листов (День 2-3).
- ✅ Ручное тестирование после завершения разработки (День 5-8).
- ✅ Регрессия (День 9-10).
- ✅ Автоматизация (в течение спринта).

### 5.4. Уровни и типы тестирования

| Уровень | Тип | Ответственный | Инструмент |
|---------|-----|---------------|------------|
| Модульное | Unit | Разработчики | JUnit / pytest |
| Интеграционное | API | Разработчики | Postman / pytest |
| Системное | Функциональное | QA | TestRail |
| Системное | Регрессионное | QA | Selenium / Cypress |
| Системное | Исследовательское | QA | — |
| Системное | UI | QA | Selenium |
| Системное | Нагрузочное | QA (опционально) | JMeter |
| Приёмочное | UAT | PO + Заказчик | — |

### 5.5. Техники тест-дизайна

| Модуль | Техника | Пример |
|--------|---------|--------|
| Каталог | Классы эквивалентности, граничные значения | Фильтр по цене: 0, 1000, 9999, 10000 |
| Корзина | Попарное тестирование | Товары, скидки, промокоды |
| Оплата | Таблица решений | Платёжные методы, статусы карт |
| Регистрация | Классы эквивалентности | Email, пароль, телефон |
| Поиск | Граничные значения | Длина запроса, спецсимволы |

### 5.6. Инструменты

| Назначение | Инструмент |
|------------|------------|
| Управление задачами | Jira |

| Unit-тесты | JUnit (Java) / pytest (Python) |
| CI/CD | Jenkins / GitHub Actions |
| Баг-трекинг | Jira |

### 5.7. Definition of Done (DoD)

**Критерии DoD для юзер-стори:**

| № | Критерий | Ответственный |
|---|----------|---------------|
| 1 | Код написан и проходит ревью | Разработчик |
| 2 | Unit-тесты написаны (покрытие ≥ 80%) | Разработчик |
| 3 | Интеграционные тесты написаны | Разработчик + QA |
| 4 | Код развёрнут на тестовом стенде | Разработчик |
| 5 | Выполнено функциональное тестирование | QA |
| 6 | Зарегистрированные баги исправлены | Команда |
| 7 | Регрессия пройдена (не сломали существующий функционал) | QA |
| 8 | Приёмочные критерии выполнены | PO + QA |
| 9 | Готово к демонстрации | PO |

### 5.8. План тестирования по дням спринта

**Спринт 1 (10 рабочих дней):**

| День | Активности QA |
|------|---------------|
| **День 1** | Анализ юзер-стори, составление чек-листов |
| **День 2** | Написание тест-кейсов в TestRail, BDD-сценариев |
| **День 3** | Подготовка тестовых данных, настройка окружения |
| **День 4** | Ручное тестирование (функциональное) — первые модули |
| **День 5** | Ручное тестирование (API, UI) — вторые модули |
| **День 6** | Исследовательское тестирование, баг-репортинг |
| **День 7** | Верификация исправленных багов |
| **День 8** | Регрессионное тестирование (ручное + авто) |
| **День 9** | Полная регрессия, проверка критических путей |
| **День 10** | Демо-подготовка, приёмочное тестирование с PO |

### 5.9. Метрики тестирования

| Метрика | Целевое значение | Способ измерения |
|---------|------------------|------------------|
| Покрытие кода тестами | ≥ 80% | JaCoCo / pytest-cov |
| Pass Rate тестов | ≥ 95% | TestRail / Jenkins |
| Количество критических багов | 0 | Jira |
| Тестовое покрытие требований | 100% | TestRail |
| Время выполнения регрессии | ≤ 1 час | Jenkins |
| Задокументированные тест-кейсы | 100% | TestRail |

### 5.10. Критерии готовности релиза

**Релиз считается готовым, если:**

| № | Критерий |
|---|----------|
| 1 | Все юзер-стори спринта выполнены и закрыты |
| 2 | Все критичные баги исправлены и закрыты |
| 3 | Функциональные тесты пройдены (100% покрытие критических сценариев) |
| 4 | Регрессионные тесты пройдены (без новых багов) |
| 5 | Приёмочные критерии согласованы с PO |
| 6 | Код развёрнут на staging-среде |
| 7 | Документация обновлена |
| 8 | Проведено smoke-тестирование на staging |
