## 1. Введение: Тестирование как часть Agile-культуры

Agile-разработка изменила подход к тестированию. Тестирование перестало быть отдельной фазой в конце проекта и стало **неотъемлемой частью каждой итерации**. В современных Agile-командах тестировщик (QA-инженер) — это не "человек, который ищет баги", а **полноправный член команды**, участвующий в планировании, анализе требований и принятии решений.

> **Ключевая идея:** В Agile тестирование — это не фаза, а **активность**, которая происходит непрерывно на протяжении всего проекта.

## 2. Scrum: Тестирование в рамках спринта

### 2.1. Структура Scrum

Scrum — это фреймворк для Agile-разработки, основанный на итерациях (спринтах) длительностью 1-4 недели.

**Основные роли Scrum:**
- **Product Owner (PO)** — отвечает за бэклог и приоритеты.
- **Scrum Master** — отвечает за соблюдение процессов.
- **Development Team** — разработчики, QA-инженеры, дизайнеры.

### 2.2. Место тестирования в Scrum-событиях

**1. Планирование спринта (Sprint Planning)**

| Действие | Участие QA |
|----------|------------|
| Выбор юзер-стори для спринта | ✅ Анализ тестируемости |
| Оценка сложности (Story Points) | ✅ Оценка тестовых задач |
| Определение критериев приёмки (Acceptance Criteria) | ✅ Совместно с PO |
| Планирование тестовых задач | ✅ Создание тестовых задач в Jira |

**Результат:** Список задач на спринт, включая тестовые задачи.

---

**2. Ежедневный стендап (Daily Standup)**

| Действие | Участие QA |
|----------|------------|
| Отчёт о прогрессе | ✅ "Что я сделал вчера для тестирования?" |
| Выявление блокировок | ✅ "Какие проблемы мешают тестированию?" |
| Координация с разработчиками | ✅ "Какой код готов к тестированию?" |

**Результат:** Синхронизация команды, выявление проблем.

---

**3. Разработка и тестирование (в течение спринта)**

**Работа QA в спринте:**
┌─────────────────────────────────────────────────────────────────┐
│ Спринт (2 недели) │
├─────────────────────────────────────────────────────────────────┤
│ День 1-2: Анализ юзер-стори, написание тест-кейсов, BDD-сценариев │
│ День 3-5: Разработчики пишут код, QA начинает ручное тестирование │
│ День 6-8: Автоматизация тестов, интеграционное тестирование │
│ День 9-10: Регрессионное тестирование, исправление багов │
│ День 11-12: Демо-подготовка, приёмочное тестирование │
└─────────────────────────────────────────────────────────────────┘

text

**Виды тестирования в спринте:**

| Вид | Исполнение | Когда |
|-----|------------|-------|
| **Unit-тесты** | Разработчики | До или во время реализации |
| **API-тесты** | QA + Разработчики | После завершения API |
| **UI-тесты** | QA | После интеграции интерфейса |
| **Регрессионные тесты** | QA (автоматизация) | Периодически в спринте |
| **Исследовательское** | QA | В течение всего спринта |

---

**4. Обзор спринта (Sprint Review / Demo)**

| Действие | Участие QA |
|----------|------------|
| Демонстрация готового функционала | ✅ Подтверждение качества |
| Проверка критериев приёмки | ✅ Валидация готовности |
| Сбор обратной связи | ✅ Запись багов и предложений |

---

**5. Ретроспектива спринта (Sprint Retrospective)**

| Действие | Участие QA |
|----------|------------|
| Анализ проблем | ✅ "Что мешало тестированию?" |
| Идентификация улучшений | ✅ "Как улучшить процессы тестирования?" |
| Планирование изменений | ✅ "Какие инструменты или практики внедрить?" |

**Результат:** Улучшение процессов в следующем спринте.

---

### 2.3. Определение готовности (DoD — Definition of Done)

**DoD** — это список критериев, которым должна соответствовать задача, чтобы считаться "готовой".

**Типичные критерии DoD с учётом тестирования:**

| Критерий | Описание |
|----------|----------|
| ✅ Код написан и проходит ревью | Разработчик |
| ✅ Написаны Unit-тесты (покрытие ≥ 80%) | Разработчик |
| ✅ Написаны интеграционные тесты | QA + Разработчик |
| ✅ Выполнено ручное тестирование | QA |
| ✅ Задокументированы тест-кейсы | QA |
| ✅ Регрессия пройдена | QA |
| ✅ Баги исправлены | Команда |
| ✅ Приёмочные критерии выполнены | PO + QA |
| ✅ Готово к демонстрации | PO |

## 3. Kanban: Тестирование в потоке

### 3.1. Что такое Kanban

**Kanban** — это Agile-фреймворк, ориентированный на **непрерывную доставку** (Continuous Delivery), где задачи перемещаются по доске (board) через колонки, представляющие этапы работы.

**Основные принципы Kanban:**
- Визуализация работы (Kanban-доска).
- Ограничение незавершённой работы (WIP — Work In Progress).
- Непрерывный поток (continuous flow).
- Непрерывное улучшение.

### 3.2. Kanban-доска с тестированием

**Типичная Kanban-доска:**
TO DO	ANALYSIS	IN PROGRESS	REVIEW	TESTING	DEPLOY	DONE
Task1						
Task2	Task3					
Task4	Task5			
Task6		
Task7	
Task8
text

**Колонки с участием QA:**

| Колонка | Описание | Роль QA |
|---------|----------|---------|
| **ANALYSIS** | Анализ требований, написание тест-кейсов | ✅ |
| **IN PROGRESS** | Разработка кода | — |
| **REVIEW** | Код-ревью, проверка качества кода | ✅ |
| **TESTING** | Ручное и автоматизированное тестирование | ✅ |
| **DEPLOY** | Развертывание, проверка в среде | ✅ |

### 3.3. Ограничение WIP и тестирование

**WIP (Work In Progress)** — ограничение на количество задач в каждой колонке.

**Пример ограничений:**
- `ANALYSIS: 2` (одновременно анализируется не более 2 задач)
- `TESTING: 3` (одновременно тестируется не более 3 задач)
- `DEPLOY: 1` (одновременно деплоится не более 1 задачи)

**Почему WIP важен для тестирования:**
- Предотвращает накопление неоттестированных задач.
- Помогает балансировать загрузку QA.
- Ускоряет обратную связь.

### 3.4. Пул-система (Pull System)

В Kanban задачи "вытягиваются" (pull) в следующую колонку, когда есть свободное место.

**Работа QA в пул-системе:**
1. Разработчик завершает задачу → перемещает в `REVIEW`.
2. QA выполняет код-ревью → перемещает в `TESTING`.
3. QA тестирует → если всё OK, перемещает в `DEPLOY`.
4. QA проверяет деплой → перемещает в `DONE`.

**Преимущество:** QA не ждёт конца спринта — тестирование происходит непрерывно.

## 4. Сравнение Scrum и Kanban с точки зрения тестирования

| Критерий | Scrum | Kanban |
|----------|-------|--------|
| **Итерации** | Спринты (1-4 недели) | Непрерывный поток |
| **Планирование тестов** | В начале каждого спринта | Постоянно |
| **Выполнение тестов** | В течение спринта | Непрерывно |
| **Регрессионное тестирование** | В конце спринта | После каждого изменения (CI/CD) |
| **Роль QA** | Часть Scrum-команды | Часть потока разработки |
| **Гибкость** | Изменения в спринте ограничены | Гибкость 24/7 |
| **Когда применять** | Проекты с релизными циклами | Проекты с непрерывной доставкой |
| **Тест-артефакты** | Отчёты по спринту | Постоянные метрики (Lead Time, Cycle Time) |

## 5. Тест-деятельности в Agile-фреймворках

### 5.1. Continuous Testing (Непрерывное тестирование)

**Continuous Testing** — это практика выполнения автоматизированных тестов на каждом этапе CI/CD-пайплайна.

**Пайплайн CI/CD с тестированием:**
КОММИТ → СБОРКА → UNIT-ТЕСТЫ → СТАТИЧЕСКИЙ АНАЛИЗ → ИНТЕГРАЦИОННЫЕ ТЕСТЫ → ДЕПЛОЙ → E2E-ТЕСТЫ

text

**Какие тесты выполняются на каждом этапе:**

| Этап | Тип тестов | Исполнение |
|------|------------|------------|
| Коммит | Unit-тесты | Автоматически (pre-commit hooks) |
| Сборка | Unit + API тесты | CI-сервер |
| Статический анализ | SonarQube, линтеры | CI-сервер |
| Интеграционные тесты | API + БД | CI-сервер |
| Деплой (в тестовую среду) | Smoke-тесты | QA |
| Деплой (в staging) | E2E-тесты | Автоматически |
| Деплой (в production) | Canary-тесты | Автоматически |

### 5.2. Тестирование как часть DoR (Definition of Ready)

**DoR (Definition of Ready)** — критерии, по которым задача готова к началу работы.

**Типичные критерии DoR с участием QA:**

| Критерий | Описание |
|----------|----------|
| ✅ Написаны приёмочные критерии (Acceptance Criteria) | PO |
| ✅ Тестируемость оценена | QA |
| ✅ Задача согласована с QA | QA |
| ✅ Нет критических зависимостей | Команда |

### 5.3. Shift-Left Testing (Тестирование "влево")

**Shift-Left** — это стратегия, при которой тестирование начинается как можно раньше (слева на временной шкале проекта).

**Уровни Shift-Left:**

| Уровень | Что делается |
|---------|--------------|
| **Уровень 1: Требования** | QA участвует в анализе и уточнении требований |
| **Уровень 2: Проектирование** | QA участвует в дизайн-ревью |
| **Уровень 3: Разработка** | QA пишет тесты параллельно с разработкой |
| **Уровень 4: CI/CD** | Автоматизация тестов в пайплайне |

**Преимущества Shift-Left:**
- Баги обнаруживаются раньше, что снижает стоимость исправления.
- Улучшается качество требований.
- QA-инженеры лучше понимают систему.

### 5.4. Shift-Right Testing (Тестирование "вправо")

**Shift-Right** — это стратегия, при которой тестирование продолжается после релиза.

**Активности Shift-Right:**

| Активность | Описание |
|------------|----------|
| **Мониторинг** | Отслеживание ошибок в production |
| **Canary-релизы** | Постепенный rollout на пользователей |
| **A/B-тестирование** | Тестирование разных версий на группах |
| **User Feedback** | Сбор обратной связи от пользователей |
| **Анализ логов** | Поиск аномалий в работе системы |

## 6. Метрики Agile-тестирования

| Метрика | Описание | Цель |
|---------|----------|------|
| **Defect Density** | Количество дефектов на объём кода | Оценка качества кода |
| **Escaped Defects** | Дефекты, найденные в production | Оценка эффективности тестирования |
| **Test Coverage** | % покрытия кода тестами | Оценка полноты тестирования |
| **Pass/Fail Rate** | % проходящих/падающих тестов | Оценка стабильности сборки |
| **Test Execution Time** | Время выполнения тестов | Оптимизация пайплайна |
| **Automation Ratio** | % автоматизированных тестов | Оценка эффективности |
| **Cycle Time** | Время от начала до релиза задачи | Оценка скорости команды |
| **Lead Time** | Время от запроса до релиза | Оценка общей скорости |

## 7. Рекомендации по тестированию в Scrum и Kanban

### 7.1. Для Scrum:

1. ✅ Включайте QA в планирование спринта и оценку задач.
2. ✅ Определяйте DoD (Definition of Done) с тестовыми критериями.
3. ✅ Автоматизируйте регрессионное тестирование.
4. ✅ Выделяйте время на исследовательское тестирование.
5. ✅ Проводите ретроспективу с акцентом на тестирование.

### 7.2. Для Kanban:

1. ✅ Визуализируйте тестовые задачи на доске.
2. ✅ Установите WIP-лимиты для колонки `TESTING`.
3. ✅ Интегрируйте автоматические тесты в CI/CD.
4. ✅ Сократите время между разработкой и тестированием (pull system).
5. ✅ Мониторьте метрики (Lead Time, Cycle Time).

### 7.3. Общие рекомендации:

1. ✅ Shift-Left: участвуйте в анализе требований.
2. ✅ Shift-Right: мониторьте production.
3. ✅ Развивайте автоматизацию.
4. ✅ Улучшайте тестовую среду (test environment).
5. ✅ Обменивайтесь знаниями в команде.

## 8. Итоговый вывод по лекции

**Тестирование в Agile — это не просто "кто-то, кто проверяет код", а неотъемлемая часть всей команды разработки.**

**Ключевые тезисы для запоминания:**

1. **Scrum:** Тестирование организовано в рамках спринтов с чёткими этапами планирования, выполнения и демонстрации.
2. **Kanban:** Тестирование непрерывно, как часть потока задач.
3. **Обе модели** требуют интеграции QA в команду и непрерывного тестирования.
4. **Shift-Left** — тестирование на ранних этапах (требования, проектирование).
5. **Shift-Right** — тестирование после релиза (мониторинг, A/B-тесты).
6. **Определение готовности (DoD)** — ключевой артефакт, объединяющий разработку и тестирование.
7. **Метрики** — помогают оценить и улучшить качество тестирования.
8. Выбор между Scrum и Kanban зависит от типа проекта и бизнес-требований.
