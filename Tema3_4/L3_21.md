## 1. Введение: Что такое тест-менеджмент

**Тест-менеджмент** — это процесс планирования, организации, контроля и анализа всех аспектов тестирования программного обеспечения. Это дисциплина, которая включает в себя управление ресурсами, сроками, артефактами и, самое главное, дефектами.

**Компоненты тест-менеджмента:**

| Компонент | Описание |
|-----------|----------|
| **Планирование** | Определение целей, стратегии, сроков и ресурсов |
| **Дизайн тестов** | Создание тест-кейсов, чек-листов, наборов данных |
| **Выполнение** | Запуск тестов, фиксация результатов, сравнение с ожидаемыми |
| **Управление дефектами** | Регистрация, отслеживание, приоритизация и закрытие багов |
| **Отчётность** | Предоставление метрик и статуса тестирования стейкхолдерам |
| **Анализ** | Оценка качества продукта и эффективности тестирования |

> **Ключевая идея:** Тест-менеджмент превращает хаотичное "поискать баги" в структурированный, измеримый и управляемый процесс.

## 2. Управление дефектами (Bug Tracking / Defect Management)

### 2.1. Жизненный цикл дефекта (Bug Lifecycle)

**Жизненный цикл дефекта** — это последовательность состояний, через которые проходит дефект от момента обнаружения до закрытия.

**Классический жизненный цикл дефекта:**

│ │ │
│ ▼ │
│ ┌─────────────┐ │
│ │ IN PROGRESS│ │
│ └─────────────┘ │
│ │ │
│ ▼ │
│ ┌─────────────┐ │
└─────────────────►│ FIXED │ │
└─────────────┘ │

└──────────┘ └──────────┘

### 2.2. Состояния дефекта (Bug Status)

| Статус | Описание | Кто устанавливает |
|--------|----------|-------------------|
| **NEW** | Дефект только что обнаружен и зарегистрирован | QA / Тестировщик |
| **ASSIGNED** | Дефект назначен на разработчика | Менеджер / Тималид |
| **IN PROGRESS** | Разработчик начал работу над исправлением | Разработчик |
| **FIXED** | Дефект исправлен, ожидает верификации | Разработчик |
| **VERIFIED** | Исправление проверено QA, ошибка устранена | QA |
| **CLOSED** | Дефект закрыт (окончательное состояние) | QA / Менеджер |
| **REOPENED** | Дефект не исправлен или воспроизвёлся снова | QA |
| **WON'T FIX** | Решено не исправлять (низкий приоритет, не влияет на бизнес) | PO / Менеджер |
| **DUPLICATE** | Дефект является дубликатом другого | QA / Менеджер |
| **INVALID** | Дефект не является багом (несоответствие ожиданиям или не воспроизводится) | QA / Менеджер |

### 2.3. Атрибуты дефекта

**Обязательные поля для регистрации дефекта:**

| Поле | Описание | Пример |
|------|----------|--------|
| **Заголовок (Summary)** | Краткое описание проблемы | "Кнопка 'Сохранить' не работает при пустом поле 'Имя'" |
| **Описание (Description)** | Подробное описание, шаги воспроизведения | "1. Открыть форму... 2. Оставить поле пустым... 3. Нажать 'Сохранить'" |
| **Приоритет (Priority)** | Важность для бизнеса (срочность исправления) | P1 (Critical), P2 (High), P3 (Medium), P4 (Low) |
| **Серьёзность (Severity)** | Влияние на функциональность | Blocker, Critical, Major, Minor, Trivial |
| **Статус (Status)** | Текущее состояние дефекта | NEW, ASSIGNED, FIXED и т.д. |
| **Окружение (Environment)** | Где обнаружен баг | Chrome 120 / Windows 11, Staging |
| **Версия (Version)** | Версия ПО | v2.3.1 |
| **Компонент (Component)** | Модуль, в котором найден баг | "Платёжный модуль" |
| **Приложенные файлы (Attachments)** | Скриншоты, видео, логи | screenshot.png, server.log |
| **Назначенный (Assignee)** | Кому назначен дефект | dev@example.com |
| **Автор (Reporter)** | Кто зарегистрировал дефект | qa@example.com |

### 2.4. Приоритет vs Серьёзность

| Понятие | Определение | Пример |
|---------|-------------|--------|
| **Приоритет (Priority)** | Важность задачи с точки зрения бизнеса | P1 = Нужно исправить в ближайшем релизе |
| **Серьёзность (Severity)** | Техническое влияние дефекта на систему | Blocker = Блокирует дальнейшее тестирование |

**Матрица Приоритет × Серьёзность:**
Серьёзность
Blocker Critical Major Minor
Приоритет
P1 Срочно Срочно Важно Средне
P2 Срочно Важно Средне Ниже
P3 Важно Средне Ниже Низко
P4 Средне Ниже Низко Низко

text

**Примеры:**

| Баг | Приоритет | Серьёзность | Почему |
|-----|-----------|-------------|--------|
| Приложение падает при запуске | P1 | Blocker | Невозможно использовать продукт |
| Неправильный цвет кнопки | P4 | Trivial | Не влияет на функциональность |
| Ошибка в расчёте налогов для VIP-клиентов | P1 | Major | Влияет на бизнес, есть обходной путь |

### 2.5. Параметры для эффективного управления дефектами

| Параметр | Что улучшает | Пример инструментов |
|----------|--------------|---------------------|
| **Трекинг** | Отслеживание статусов | Jira, Bugzilla, YouTrack |
| **Авто-нотификации** | Уведомления об изменениях | Email-оповещения в Jira |
| **Фильтры и поиск** | Быстрый поиск багов | JQL (Jira Query Language) |
| **Интеграция с CI/CD** | Автоматическое создание багов при падении тестов | Jenkins + Jira |
| **Дашборды** | Визуализация состояния | Jira Dashboards, TestRail Reports |
| **Анализ трендов** | Понимание динамики дефектов | Отчёты по новым/закрытым багам |

3.3. TestRail — специализированный тест-менеджмент
TestRail — инструмент для управления тестовой документацией, выполнения тестов и создания отчётов.

Ключевые возможности TestRail:

Возможность	Описание
Test Cases	Создание и управление тест-кейсами
Test Suites	Группировка тест-кейсов по модулям
Test Runs	Выполнение наборов тестов для конкретных релизов
Test Plans	Объединение нескольких Test Runs
Reports	Отчёты по статусам тестов, покрытию, дефектам
Integrations	Jira, GitHub, Jenkins, Slack
API	Автоматизация загрузки и выгрузки тестов
Bulk Operations	Массовое обновление тестов
Структура TestRail:

text
Проект (Project)
  └── Тестовая Suite (Test Suite)
       └── Раздел (Section)
            └── Тест-кейс (Test Case)
                 ├── Шаги (Steps)
                 ├── Ожидаемый результат (Expected Result)
                 └── Статус (Pass/Fail/Blocked/Untested)
Пример тест-кейса в TestRail:

Поле	Значение
ID	TC-1001
Название	Проверка входа в систему с правильными данными
Приоритет	Высокий
Тип	Функциональный
Шаг 1	Открыть страницу входа	Ожидание: Страница загружена
Шаг 2	Ввести логин "user@example.com"	Ожидание: Поле заполнено
Шаг 3	Ввести пароль "password123"	Ожидание: Поле заполнено
Шаг 4	Нажать "Войти"	Ожидание: Перенаправление на главную страницу
Интеграция TestRail с Jira:

Двусторонняя синхронизация: Связывает тест-кейсы и баги.

Автоматическое создание багов: При падении теста в TestRail создаётся баг в Jira.

Отслеживание покрытия: Видно, какие тесты покрывают какие требования.

3.4. Xray — тест-менеджмент внутри Jira
Xray — это плагин для Jira, который добавляет возможности управления тестами.

Ключевые особенности Xray:

Особенность	Описание
Интеграция с Jira	Тесты, планы и запуски хранятся в Jira
BDD поддержка	Cucumber, Gherkin
Автоматизация	Запуск тестов из Jenkins, GitLab CI
Отчёты	Покрытие, тренды, статусы
Гибкие настройки	Настраиваемые статусы и переходы
Типы задач в Xray:

Тип	Описание
Test	Тест-кейс
Test Set	Группа тестов
Test Plan	План тестирования
Test Execution	Запуск тестов
Pre-Condition	Предусловия для теста
Пример Workflow в Xray:

text
Test (NEW) → Test (READY) → Test Execution (RUNNING) → Test Execution (PASSED/FAILED) → Bug (CREATED)

4. Процесс тест-менеджмента на практике
Жизненный цикл тестирования в инструментах:

text
1. Планирование
   ├── Создание проекта в Jira
   ├── Создание Test Plan в TestRail
   └── Определение стратегии тестирования

2. Дизайн
   ├── Создание Test Cases в TestRail/Xray
   ├── Привязка к User Stories в Jira
   └── Ревью тест-кейсов

3. Выполнение
   ├── Запуск Test Run в TestRail
   ├── Выполнение тестов (ручных/автоматических)
   ├── Фиксация результатов (Pass/Fail/Blocked)
   └── Создание багов в Jira при падении

4. Отслеживание дефектов
   ├── Обработка багов в Jira
   ├── Назначение разработчикам
   ├── Исправление и верификация
   └── Закрытие (или переоткрытие)

5. Отчётность
   ├── Автоматические отчёты в TestRail
   ├── Графики и дашборды в Jira
   └── Предоставление статуса команде
5. Метрики тест-менеджмента
Метрика	Формула	Цель
Defect Density	Количество дефектов / LOC (строк кода)	Оценка качества кода
Defect Open Rate	Новые дефекты / время	Скорость обнаружения багов
Defect Close Rate	Закрытые дефекты / время	Скорость исправления багов
Fixed vs Open Ratio	Исправленные / Открытые	Прогресс исправлений
Critical Defects	Количество критических багов	Качество релиза
Test Execution Coverage	Выполненные тесты / Все тесты (%)	Прогресс тестирования
Pass Rate	Прошедшие тесты / Выполненные тесты (%)	Стабильность сборки
Automation Ratio	Автоматизированные / Все тесты (%)	Эффективность автоматизации
Mean Time to Detect (MTTD)	Среднее время обнаружения дефекта	Эффективность тестирования
Mean Time to Repair (MTTR)	Среднее время исправления дефекта	Эффективность разработки

6.1. Правила написания баг-репорта
Хороший заголовок: Кратко, ясно, отражает суть проблемы.

✅ "Кнопка 'Сохранить' неактивна при заполнении всех полей"

❌ "Не работает форма"

Чёткие шаги воспроизведения: Пошаговая инструкция.

✅ "1. Открыть страницу регистрации. 2. Заполнить все поля. 3. Нажать 'Сохранить'."

❌ "Попробуйте сохранить форму"

Ожидаемый результат: Что должно было произойти.

✅ "Форма сохраняется, появляется сообщение об успехе"

❌ "Форма должна работать"

Фактический результат: Что произошло на самом деле.

✅ "Кнопка 'Сохранить' остаётся неактивной, форма не сохраняется"

❌ "Кнопка не работает"

Приложения: Скриншоты, видео, логи.

✅ Скриншот с выделенной кнопкой, фрагмент лога

❌ Только текст

7. Итоговый вывод по лекции
Тест-менеджмент — это системный подход к организации тестирования, позволяющий контролировать качество продукта на всех этапах разработки.

Ключевые тезисы для запоминания:

Тест-менеджмент включает планирование, дизайн, выполнение, управление дефектами и отчётность.

Управление дефектами — ключевой процесс, обеспечивающий качество продукта.

Жизненный цикл дефекта включает состояния: NEW → ASSIGNED → IN PROGRESS → FIXED → VERIFIED → CLOSED.
