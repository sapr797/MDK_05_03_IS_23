## 1. Введение: Почему абстрактные классы и интерфейсы — особый случай

Абстрактные классы и интерфейсы являются фундаментальными элементами объектно-ориентированного проектирования. Они определяют контракты, которые должны выполнять конкретные реализации. Однако их тестирование представляет собой уникальную задачу:

- **Абстрактные классы** содержат частичную реализацию, которую нельзя протестировать напрямую, так как они не могут быть инстанцированы.
- **Интерфейсы** вообще не содержат реализации и не могут быть протестированы сами по себе.

> **Ключевая идея:** Тестирование абстрактных классов и интерфейсов — это тестирование **контракта**, который должны соблюдать все реализации.

## 2. Особенности тестирования абстрактных классов

### 2.1. Что нужно тестировать в абстрактном классе

| Компонент | Необходимость тестирования | Сложность |
|-----------|---------------------------|-----------|
| Конкретные методы (с реализацией) | Высокая | Средняя |
| Абстрактные методы | Нет (тестируются в реализациях) | Н/Д |
| Поля (состояние) | Высокая | Высокая |
| Конструкторы | Высокая | Средняя |
| Инварианты | Высокая | Высокая |
| Защищённые методы | Высокая | Высокая |

### 2.2. Стратегии тестирования абстрактных классов

#### Стратегия 1: Создание конкретной тестовой реализации

**Идея:** Создать специальный класс-наследник, который реализует все абстрактные методы, и использовать его для тестирования.

```java
public abstract class AbstractStack {
    protected List<Object> elements = new ArrayList<>();
    
    public abstract void push(Object element);
    public abstract Object pop();
    
    // Конкретный метод с реализацией
    public boolean isEmpty() {
        return elements.isEmpty();
    }
    
    // Конкретный метод с реализацией
    public int size() {
        return elements.size();
    }
}

// Тестовая реализация
class TestableStack extends AbstractStack {
    @Override
    public void push(Object element) {
        elements.add(element);
    }
    
    @Override
    public Object pop() {
        if (isEmpty()) return null;
        return elements.remove(elements.size() - 1);
    }
}
Преимущества:

Полный контроль над реализацией.

Можно сосредоточиться только на тестировании абстрактного класса.

Недостатки:

Дополнительный код для тестов.

Тестовая реализация может внести свои ошибки.

Стратегия 2: Использование существующих реализаций
Идея: Использовать одну из конкретных реализаций абстрактного класса для тестирования его поведения.

java
@Test
void testIsEmpty_UsingArrayListImplementation() {
    AbstractStack stack = new ArrayListStack(); // Существующая реализация
    assertTrue(stack.isEmpty());
    stack.push("test");
    assertFalse(stack.isEmpty());
}
Преимущества:

Нет необходимости в дополнительном коде.

Тестируется реальное использование.

Недостатки:

Поведение зависит от конкретной реализации.

Не все части абстрактного класса могут быть протестированы.

Стратегия 3: Использование mock-объектов
Идея: Создать mock-объект абстрактного класса с помощью библиотеки мокинга.

java
@Test
void testAbstractClassWithMock() {
    AbstractStack mockStack = mock(AbstractStack.class);
    
    // Настройка поведения
    when(mockStack.size()).thenReturn(10);
    when(mockStack.isEmpty()).thenCallRealMethod();
    
    // Проверка
    assertFalse(mockStack.isEmpty());
}
Преимущества:

Быстро и гибко.

Можно изолировать тестируемый метод.

Недостатки:

Не проверяет реальное состояние.

Может быть сложно для сложных классов.

2.3. Тестирование защищённых методов
Защищённые (protected) методы абстрактного класса часто содержат важную логику, которую нужно тестировать.

Проблема: Защищённые методы недоступны из тестового класса, который находится в другом пакете.

Решения:

Поместить тестовый класс в тот же пакет.

java
// src/main/java/com/example/AbstractClass.java
package com.example;

public abstract class AbstractClass {
    protected int calculate(int a, int b) {
        return a + b;
    }
}

// src/test/java/com/example/AbstractClassTest.java
package com.example;

class TestableClass extends AbstractClass {
    @Override
    public void abstractMethod() { /* реализация */ }
}

class AbstractClassTest {
    @Test
    void testCalculate() {
        TestableClass obj = new TestableClass();
        assertEquals(5, obj.calculate(2, 3)); // protected доступен в том же пакете
    }
}
Использовать рефлексию.

java
@Test
void testProtectedMethod_UsingReflection() throws Exception {
    TestableClass obj = new TestableClass();
    Method method = AbstractClass.class.getDeclaredMethod("calculate", int.class, int.class);
    method.setAccessible(true);
    int result = (int) method.invoke(obj, 2, 3);
    assertEquals(5, result);
}
Использовать @VisibleForTesting.

java
import com.google.common.annotations.VisibleForTesting;

public abstract class AbstractClass {
    @VisibleForTesting
    protected int calculate(int a, int b) {
        return a + b;
    }
}
2.4. Тестирование конструкторов абстрактных классов
Конструкторы абстрактных классов вызываются при создании объектов производных классов и могут содержать важную логику инициализации.

Пример:

java
public abstract class AbstractConnection {
    protected String url;
    protected int timeout;
    protected boolean isConnected;
    
    public AbstractConnection(String url, int timeout) {
        if (url == null || url.isEmpty()) {
            throw new IllegalArgumentException("URL cannot be null or empty");
        }
        if (timeout <= 0) {
            throw new IllegalArgumentException("Timeout must be positive");
        }
        this.url = url;
        this.timeout = timeout;
        this.isConnected = false;
    }
}

// Тест
@Test
void testConstructor_ValidParameters() {
    TestableConnection connection = new TestableConnection("http://example.com", 5000);
    assertEquals("http://example.com", connection.getUrl());
    assertEquals(5000, connection.getTimeout());
    assertFalse(connection.isConnected());
}

@Test
void testConstructor_InvalidUrl() {
    assertThrows(IllegalArgumentException.class, () -> {
        new TestableConnection(null, 5000);
    });
    assertThrows(IllegalArgumentException.class, () -> {
        new TestableConnection("", 5000);
    });
}

@Test
void testConstructor_InvalidTimeout() {
    assertThrows(IllegalArgumentException.class, () -> {
        new TestableConnection("http://example.com", -1);
    });
}
3. Особенности тестирования интерфейсов
3.1. Что можно тестировать в интерфейсе
Интерфейс не содержит реализации, поэтому напрямую протестировать его невозможно. Однако можно тестировать:

Аспект	Описание
Контракт интерфейса	Проверка, что все реализации соблюдают контракт
default-методы (Java 8+)	Методы с реализацией по умолчанию
static-методы (Java 8+)	Статические методы интерфейса
Инварианты	Условия, которые должны выполняться для всех реализаций
3.2. Тестирование контракта интерфейса
Контракт интерфейса — это набор правил и ожиданий, которые должны соблюдать все реализации.

Пример: Интерфейс List

java
public interface SimpleList<E> {
    boolean add(E element);
    boolean remove(Object o);
    E get(int index);
    int size();
    boolean contains(Object o);
    boolean isEmpty();
}
Контракт:

add(): возвращает true, если элемент добавлен, false в противном случае.

remove(): возвращает true, если элемент удалён, false в противном случае.

get(): возвращает элемент по индексу, выбрасывает IndexOutOfBoundsException при неверном индексе.

size(): возвращает количество элементов.

contains(): возвращает true, если элемент есть в списке.

isEmpty(): возвращает true, если список пуст.

3.3. Шаблон "Интерфейсный контрактный тест"
Идея: Создать абстрактный тестовый класс, который определяет тесты для интерфейса, и затем наследовать его для каждой реализации.

java
// Базовый тест для интерфейса
public abstract class SimpleListContractTest<E> {
    
    // Абстрактный фабричный метод
    protected abstract SimpleList<E> createList();
    protected abstract E createElement();
    protected abstract E createDifferentElement();
    
    @Test
    void testNewList_IsEmpty() {
        SimpleList<E> list = createList();
        assertTrue(list.isEmpty());
        assertEquals(0, list.size());
    }
    
    @Test
    void testAdd_ReturnsTrue() {
        SimpleList<E> list = createList();
        assertTrue(list.add(createElement()));
    }
    
    @Test
    void testAdd_IncreasesSize() {
        SimpleList<E> list = createList();
        int sizeBefore = list.size();
        list.add(createElement());
        assertEquals(sizeBefore + 1, list.size());
    }
    
    @Test
    void testAdd_ContainsElement() {
        SimpleList<E> list = createList();
        E element = createElement();
        list.add(element);
        assertTrue(list.contains(element));
    }
    
    @Test
    void testGet_ValidIndex_ReturnsElement() {
        SimpleList<E> list = createList();
        E element = createElement();
        list.add(element);
        assertEquals(element, list.get(0));
    }
    
    @Test
    void testGet_InvalidIndex_ThrowsException() {
        SimpleList<E> list = createList();
        assertThrows(IndexOutOfBoundsException.class, () -> list.get(-1));
        assertThrows(IndexOutOfBoundsException.class, () -> list.get(0));
    }
    
    @Test
    void testRemove_ExistingElement_ReturnsTrue() {
        SimpleList<E> list = createList();
        E element = createElement();
        list.add(element);
        assertTrue(list.remove(element));
    }
    
    @Test
    void testRemove_NonExistingElement_ReturnsFalse() {
        SimpleList<E> list = createList();
        list.add(createElement());
        assertFalse(list.remove(createDifferentElement()));
    }
    
    @Test
    void testRemove_DecreasesSize() {
        SimpleList<E> list = createList();
        E element = createElement();
        list.add(element);
        int sizeBefore = list.size();
        list.remove(element);
        assertEquals(sizeBefore - 1, list.size());
    }
}

// Реализация теста для конкретного класса
public class ArrayListTest extends SimpleListContractTest<String> {
    
    @Override
    protected SimpleList<String> createList() {
        return new ArrayList<>();
    }
    
    @Override
    protected String createElement() {
        return "test";
    }
    
    @Override
    protected String createDifferentElement() {
        return "different";
    }
}
3.4. Тестирование default-методов интерфейсов
Начиная с Java 8, интерфейсы могут содержать методы с реализацией по умолчанию.

Пример:

java
public interface Identifiable {
    Long getId();
    
    // default-метод
    default boolean hasSameId(Identifiable other) {
        return this.getId().equals(other.getId());
    }
}
Тестирование default-метода:

java
// Тестовая реализация
class TestIdentifiable implements Identifiable {
    private Long id;
    
    public TestIdentifiable(Long id) {
        this.id = id;
    }
    
    @Override
    public Long getId() {
        return id;
    }
}

class IdentifiableTest {
    
    @Test
    void testHasSameId_SameIds_ReturnsTrue() {
        TestIdentifiable obj1 = new TestIdentifiable(1L);
        TestIdentifiable obj2 = new TestIdentifiable(1L);
        assertTrue(obj1.hasSameId(obj2));
    }
    
    @Test
    void testHasSameId_DifferentIds_ReturnsFalse() {
        TestIdentifiable obj1 = new TestIdentifiable(1L);
        TestIdentifiable obj2 = new TestIdentifiable(2L);
        assertFalse(obj1.hasSameId(obj2));
    }
    
    @Test
    void testHasSameId_NullOther_ThrowsException() {
        TestIdentifiable obj1 = new TestIdentifiable(1L);
        assertThrows(NullPointerException.class, () -> obj1.hasSameId(null));
    }
}
Важно: Каждая реализация интерфейса наследует default-метод, поэтому его нужно тестировать только один раз в контрактном тесте.

4. Сравнение подходов
4.1. Абстрактные классы vs Интерфейсы для тестирования
Аспект	Абстрактный класс	Интерфейс
Можно ли инстанцировать	Нет	Нет
Содержит ли реализацию	Да (частичную)	Только default-методы (Java 8+)
Что тестируем	Реализацию конкретных методов	Контракт и default-методы
Основная стратегия	Создание тестовой реализации	Контрактное тестирование
Сложность	Высокая	Средняя
5. Практические рекомендации
5.1. Проектирование для тестируемости
Делайте конструкторы защищёнными — это позволяет создавать тестовые подклассы.

Выносите сложную логику в отдельные методы — их легче тестировать.

Используйте фабричные методы для создания объектов.

Документируйте инварианты — это помогает создавать корректные тесты.

6. Итоговый вывод по лекции
Тестирование абстрактных классов и интерфейсов — это тестирование контрактов и общей логики, которая будет использоваться множеством реализаций.

Ключевые тезисы для запоминания:

Абстрактные классы тестируются через конкретную тестовую реализацию или через существующие реализации.

Интерфейсы тестируются через контрактные тесты, которые проверяют все реализации.

Защищённые методы абстрактных классов требуют специальных подходов (один пакет, рефлексия, @VisibleForTesting).

default-методы интерфейсов тестируются один раз в контрактном тесте.

Конструкторы абстрактных классов должны быть тщательно протестированы.

Шаблон контрактного тестирования — это стандартный способ тестирования интерфейсов.

Инварианты должны быть проверены для всех реализаций.

Задание: Разработать контрактные тесты для интерфейса и тесты для абстрактного класса.

Интерфейс:

java
public interface Cache<K, V> {
    V get(K key);
    void put(K key, V value);
    boolean containsKey(K key);
    V remove(K key);
    void clear();
    int size();
    boolean isEmpty();
}
Абстрактный класс:

java
public abstract class AbstractCache<K, V> implements Cache<K, V> {
    protected Map<K, V> storage = new HashMap<>();
    protected int maxSize;
    protected long timeToLive;
    protected Map<K, Long> expirationTimes;
    
    public AbstractCache(int maxSize, long timeToLive) {
        this.maxSize = maxSize;
        this.timeToLive = timeToLive;
        this.expirationTimes = new HashMap<>();
    }
    
    public abstract void evict();
    
    // Конкретный метод с реализацией
    public boolean isExpired(K key) {
        Long expirationTime = expirationTimes.get(key);
        if (expirationTime == null) return false;
        return System.currentTimeMillis() > expirationTime;
    }
    
    @Override
    public V get(K key) {
        if (isExpired(key)) {
            storage.remove(key);
            expirationTimes.remove(key);
            return null;
        }
        return storage.get(key);
    }
    
    @Override
    public void put(K key, V value) {
        if (storage.size() >= maxSize) {
            evict();
        }
        storage.put(key, value);
        expirationTimes.put(key, System.currentTimeMillis() + timeToLive);
    }
    
    @Override
    public boolean containsKey(K key) {
        if (isExpired(key)) {
            storage.remove(key);
            expirationTimes.remove(key);
            return false;
        }
        return storage.containsKey(key);
    }
}
