## 1. Введение: Сложность тестирования иерархий

Наследование и полиморфизм — это фундаментальные механизмы объектно-ориентированного программирования, которые обеспечивают переиспользование кода и гибкость архитектуры. Однако именно эти механизмы создают наибольшие сложности при тестировании.

**Основные проблемы:**

1. **Наследование:** Изменения в базовом классе могут незаметно нарушить работу всех производных классов.
2. **Полиморфизм:** Один и тот же вызов метода может выполнять разные реализации, и сложно гарантировать, что все они протестированы.
3. **Скрытое поведение:** Производные классы наследуют поведение, которое может быть не очевидно из их кода.
4. **Динамическое связывание:** Решение о том, какая реализация метода будет вызвана, принимается во время выполнения, что усложняет анализ.

> **Ключевая идея:** При тестировании иерархий классов нужно проверять не только каждый класс в отдельности, но и **все контексты использования**, в которых объект может оказаться.

## 2. Особенности наследования, влияющие на тестирование

### 2.1. Наследование методов

Когда класс наследует метод от родителя, этот метод **физически не присутствует** в коде производного класса, но является его полноценной частью.

**Влияние на тестирование:**

| Аспект | Описание |
|--------|----------|
| **Скрытый код** | Метод существует в производном классе, но его код находится в другом месте. |
| **Повторное тестирование** | Унаследованный метод должен быть протестирован в контексте производного класса. |
| **Изменение поведения** | Метод может переопределяться, что требует новых тестов. |

**Пример проблемы:**

```java
public class Animal {
    public String makeSound() {
        return "Some sound";
    }
}

public class Dog extends Animal {
    // Наследует makeSound() без переопределения
}

public class Cat extends Animal {
    @Override
    public String makeSound() {
        return "Meow";
    }
}
Тестовые требования:

Animal.makeSound() тестируется в AnimalTest.

Dog.makeSound() наследует метод — должен быть протестирован в DogTest (повторно).

Cat.makeSound() переопределяет метод — должен быть протестирован в CatTest.

2.2. Наследование полей
Поля также наследуются, и их состояние может влиять на поведение унаследованных методов.

Пример:

java
public class Vehicle {
    protected int speed;
    protected int maxSpeed;
    
    public void accelerate() {
        if (speed < maxSpeed) {
            speed += 10;
        }
    }
}

public class SportsCar extends Vehicle {
    private boolean turboMode;
    
    @Override
    public void accelerate() {
        if (turboMode) {
            speed += 20;
        } else {
            super.accelerate();
        }
    }
}
Сложность: Состояние полей родительского класса влияет на поведение методов производного класса.

2.3. Иерархия вызовов конструкторов
Конструктор производного класса всегда вызывает конструктор родительского класса (явно или неявно). Это создаёт цепочку инициализаций, которую нужно тестировать.

Пример:

java
public class A {
    private int value;
    public A(int value) { this.value = value; }
}

public class B extends A {
    private String name;
    public B(int value, String name) {
        super(value);  // Явный вызов
        this.name = name;
    }
}

public class C extends B {
    private double factor;
    public C(int value, String name, double factor) {
        super(value, name);  // Явный вызов
        this.factor = factor;
    }
}
Тестовые требования:

Проверить, что конструктор A корректно инициализирует своё состояние.

Проверить, что конструктор B вызывает конструктор A с правильными параметрами.

Проверить, что конструктор C вызывает конструктор B с правильными параметрами.

Проверить конечное состояние объекта C после полной инициализации.

2.4. Видимость методов и полей (protected, private, public)
Модификаторы доступа влияют на то, какие методы и поля доступны в производных классах.

Модификатор	Доступ для производных классов	Влияние на тестирование
public	Доступен	Тестирование стандартное
protected	Доступен	Может быть переопределён
private	Недоступен	Не может быть переопределён, но влияет на состояние
package-private	Доступен, если в том же пакете	Зависит от пакета
Проблема: private поля родительского класса не видны в производном классе, но их состояние влияет на поведение унаследованных методов. Проверить их можно только через публичные методы или механизмы рефлексии.

3. Стратегии тестирования иерархий классов
3.1. Инкрементное тестирование (Incremental Testing)
Идея: Тестировать иерархию классов постепенно, начиная с базовых классов и переходя к производным.

Алгоритм:

Тестирование базового класса: Полное тестирование всех методов и инвариантов.

Тестирование производного класса:

Протестировать все унаследованные методы (повторно) для проверки корректности в новом контексте.

Протестировать все новые методы.

Протестировать все переопределённые методы.

Проверить инварианты производного класса.

Продолжить для всех уровней иерархии.

Преимущества:

Ошибки обнаруживаются на ранних стадиях.

Легко локализовать проблему.

3.2. Стратегия "Каждый класс отдельно" (Class-Level Testing)
Идея: Тестировать каждый класс как независимый компонент, создавая для него полный набор тестов, даже если многие методы унаследованы.

Требования:

Для каждого класса создаётся отдельный тестовый класс.

Тесты для унаследованных методов дублируются (или используются общие тестовые утилиты).

Тесты для производных классов должны учитывать специфику их состояния.

Пример структуры тестов:

text
src/test/java/
├── AnimalTest.java          // Тесты для Animal
├── DogTest.java             // Тесты для Dog (включая унаследованные)
├── CatTest.java             // Тесты для Cat (включая унаследованные)
└── common/
    └── AnimalTestBase.java  // Общие тесты для всех животных
3.3. Стратегия "Параметризованное тестирование"
Идея: Использовать параметризованные тесты для проверки всех классов иерархии с одинаковыми сценариями.

Пример с JUnit 5:

java
@ParameterizedTest
@MethodSource("animalProvider")
void testMakeSound(Animal animal, String expectedSound) {
    assertEquals(expectedSound, animal.makeSound());
}

static Stream<Arguments> animalProvider() {
    return Stream.of(
        Arguments.of(new Animal(), "Some sound"),
        Arguments.of(new Dog(), "Woof"),
        Arguments.of(new Cat(), "Meow")
    );
}
Преимущества:

Единый набор тестов для всей иерархии.

Легко добавить новый класс.

Недостатки:

Не все тесты подходят для всех классов (специфическое поведение требует отдельных тестов).

3.4. Стратегия "Тестирование через интерфейсы"
Идея: Тестировать поведение через интерфейсы, а не конкретные классы.

Подход:

java
public interface Animal {
    String makeSound();
    String getName();
    int getAge();
}

// Тесты пишутся для интерфейса
class AnimalContractTest {
    
    @Test
    void testMakeSound_NotNull(Animal animal) {
        assertNotNull(animal.makeSound());
    }
    
    @Test
    void testGetName_NotNull(Animal animal) {
        assertNotNull(animal.getName());
    }
    
    // Проверка инвариантов через интерфейс
    @Test
    void testAgeRange(Animal animal) {
        int age = animal.getAge();
        assertTrue(age >= 0 && age <= 100);
    }
}

// Тесты для конкретных классов
class DogTest extends AnimalContractTest {
    @Test
    void testMakeSound_DogSpecific() {
        Dog dog = new Dog();
        assertEquals("Woof", dog.makeSound());
    }
}
Преимущества:

Гарантирует, что все реализации соответствуют контракту.

Упрощает добавление новых реализаций.

4. Тестирование полиморфизма
4.1. Суть проблемы
Полиморфизм означает, что один и тот же вызов метода может привести к выполнению разных реализаций в зависимости от фактического типа объекта.

java
Animal animal = getAnimal(); // Может вернуть Dog, Cat или Animal
animal.makeSound();          // Какая реализация будет вызвана?
Проблема для тестирования:

Нельзя гарантировать, что все возможные реализации будут протестированы.

Статический анализ не может определить все контексты использования.

4.2. Стратегия "Покрытие всех реализаций"
Идея: Для каждого полиморфного вызова необходимо протестировать все возможные реализации.

Алгоритм:

Идентификация полиморфных вызовов: Найти все места в коде, где используется полиморфизм.

Определение всех реализаций: Составить список всех классов, которые могут быть подставлены в данном контексте.

Создание тестов: Для каждого контекста выполнить тесты со всеми реализациями.

Пример:

java
public class AnimalService {
    public void processAnimal(Animal animal) {
        // Полиморфный вызов
        String sound = animal.makeSound();
        // ...
    }
}

// Тест должен проверить processAnimal() с:
// - Animal
// - Dog
// - Cat
// - (любыми другими реализациями)
Реализация теста:

java
@ParameterizedTest
@MethodSource("animalProvider")
void testProcessAnimal(Animal animal) {
    AnimalService service = new AnimalService();
    service.processAnimal(animal);
    // Проверки...
}
4.3. Стратегия "Тестирование динамического связывания"
Идея: Проверить, что динамическое связывание работает корректно и вызывается правильная реализация метода.

Тестовые сценарии:

Прямой вызов: Вызов метода на объекте известного типа.

Вызов через интерфейс: Вызов метода через интерфейс/абстрактный класс.

Вызов из базового класса: Метод базового класса вызывает переопределённый метод.

Вызов в коллекциях: Объекты разных типов в одной коллекции.

Пример:

java
@Test
void testDynamicBinding_DirectCall() {
    Dog dog = new Dog();
    assertEquals("Woof", dog.makeSound());
}

@Test
void testDynamicBinding_ThroughInterface() {
    Animal animal = new Cat();
    assertEquals("Meow", animal.makeSound());
}

@Test
void testDynamicBinding_FromSuperclass() {
    Cat cat = new Cat();
    // Базовый метод вызывает переопределённый
    assertEquals("Cat says Meow", cat.describe());
}

@Test
void testDynamicBinding_Collection() {
    List<Animal> animals = Arrays.asList(new Dog(), new Cat(), new Animal());
    for (Animal animal : animals) {
        // Каждый объект должен вести себя по-своему
        assertNotNull(animal.makeSound());
    }
}
4.4. Стратегия "Проверка контракта LSP"
Принцип подстановки Лисков (Liskov Substitution Principle, LSP): Объекты производного класса должны быть заменяемы объектами базового класса без изменения корректности программы.

Влияние на тестирование: Необходимо проверить, что производный класс соблюдает контракт базового класса.

Пример нарушения LSP:

java
public class Rectangle {
    protected int width;
    protected int height;
    
    public void setWidth(int width) { this.width = width; }
    public void setHeight(int height) { this.height = height; }
    public int getArea() { return width * height; }
}

public class Square extends Rectangle {
    @Override
    public void setWidth(int width) {
        super.setWidth(width);
        super.setHeight(width);  // Нарушение LSP!
    }
    
    @Override
    public void setHeight(int height) {
        super.setHeight(height);
        super.setWidth(height);  // Нарушение LSP!
    }
}
Тест, выявляющий нарушение LSP:

java
@Test
void testLSP_Rectangle() {
    Rectangle rect = new Square();  // Подстановка
    rect.setWidth(5);
    rect.setHeight(10);
    // Ожидаемая площадь: 5 * 10 = 50
    // Фактическая площадь: 10 * 10 = 100
    assertEquals(50, rect.getArea());  // Тест провалится!
}
Стратегия тестирования LSP:

Тесты базового класса должны проходить для всех производных классов.

Тесты производного класса не должны нарушать контракт базового.

5. Практические рекомендации
5.1. Проектирование тестируемой иерархии
Тестируйте абстрактные классы: Создайте конкретную реализацию-заглушку для тестирования абстрактного класса.

Используйте тестовые фабрики: Создавайте объекты через фабричные методы для упрощения тестов.

Документируйте контракты: Явно документируйте ожидаемое поведение для всех реализаций.

5.2. Организация тестового кода
text
src/test/java/
├── com/example/animals/
│   ├── AnimalTest.java          // Базовые тесты
│   ├── DogTest.java             // Специфические тесты
│   ├── CatTest.java             // Специфические тесты
│   └── AnimalContractTest.java  // Контрактные тесты
├── com/example/vehicles/
│   ├── VehicleTest.java
│   ├── CarTest.java
│   └── ...
└── common/
    ├── BaseTest.java            // Общие утилиты
    └── TestFactory.java         // Фабрика объектов
5.3. Автоматизация проверки покрытия иерархии
Используйте инструменты для анализа покрытия, чтобы убедиться, что все классы иерархии протестированы:

JaCoCo / Cobertura: Покрытие кода.

SonarQube: Анализ покрытия и выявление непротестированных классов.

IntelliJ IDEA Test Coverage: Визуализация покрытия.

6. Сравнение подходов
Подход	Преимущества	Недостатки	Когда применять
Инкрементное тестирование	Раннее обнаружение ошибок, локализация проблем	Требует много тестов	Большие иерархии
Каждый класс отдельно	Полное покрытие, независимость	Дублирование тестов	Все иерархии
Параметризованное	Минимум дублирования, легкость добавления новых классов	Сложность со специфическими тестами	Иерархии с единообразным поведением
Через интерфейсы	Проверка контракта, гибкость	Не проверяет специфическое поведение	Иерархии с общим интерфейсом
7. Итоговый вывод по лекции
Тестирование иерархий классов и полиморфизма — это одна из самых сложных областей объектно-ориентированного тестирования.

Ключевые тезисы для запоминания:

Наследование требует повторного тестирования унаследованных методов в контексте производных классов.

Полиморфизм требует тестирования всех реализаций во всех контекстах использования.

Принцип LSP должен быть проверен тестами: производные классы должны соблюдать контракт базовых.

Используйте несколько стратегий для разных ситуаций: инкрементное тестирование, параметризованные тесты, тестирование через интерфейсы.

Автоматизация (параметризованные тесты, фабрики, контрактные тесты) помогает справиться со сложностью.

Покрытие кода — важный метрический показатель для оценки полноты тестирования иерархии.
