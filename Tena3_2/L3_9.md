## 1. Введение: Почему паттерны проектирования требуют особого подхода к тестированию

Паттерны проектирования (Design Patterns) — это проверенные решения типовых задач в объектно-ориентированном проектировании. Они повышают гибкость, переиспользуемость и поддерживаемость кода. Однако именно эти качества создают дополнительные сложности при тестировании.

Среди множества паттернов особое место занимают **порождающие паттерны** (в частности, **Factory**) и **поведенческие паттерны** (в частности, **Strategy**), поскольку они напрямую влияют на создание объектов и выбор алгоритмов, что критически важно для корректной работы системы.

## 2. Паттерн Factory (Фабрика)

### 2.1. Определение и варианты

**Паттерн Factory** — это порождающий паттерн, который предоставляет интерфейс для создания объектов, позволяя подклассам решать, какой класс инстанцировать.

**Основные вариации:**

| Вариант | Описание | Пример |
|---------|----------|--------|
| **Simple Factory** | Статический метод, создающий объекты на основе параметра | `createDocument(type)` |
| **Factory Method** | Абстрактный метод, реализуемый подклассами | `DocumentCreator.createDocument()` |
| **Abstract Factory** | Интерфейс для создания семейств связанных объектов | `GUIFactory.createButton()`, `createWindow()` |

### 2.2. Особенности тестирования Factory-паттернов

**Ключевые аспекты тестирования:**

| Аспект | Описание |
|--------|----------|
| **Корректность создания** | Проверка, что фабрика создаёт объект правильного типа |
| **Параметры создания** | Проверка, что объект создаётся с корректными параметрами |
| **Обработка ошибок** | Проверка поведения при невалидных параметрах |
| **Состояние объекта** | Проверка, что созданный объект находится в корректном состоянии |
| **Инварианты** | Проверка, что все инварианты созданного объекта соблюдены |
| **Побочные эффекты** | Проверка, что фабрика не имеет нежелательных побочных эффектов |

### 2.3. Пример 1: Тестирование Simple Factory

**Код:**

```java
public enum DocumentType {
    WORD, PDF, EXCEL, IMAGE
}

public class DocumentFactory {
    public static Document createDocument(DocumentType type, String name) {
        if (type == null) {
            throw new IllegalArgumentException("Document type cannot be null");
        }
        if (name == null || name.isEmpty()) {
            throw new IllegalArgumentException("Document name cannot be null or empty");
        }
        
        switch (type) {
            case WORD:
                return new WordDocument(name);
            case PDF:
                return new PdfDocument(name);
            case EXCEL:
                return new ExcelDocument(name);
            case IMAGE:
                return new ImageDocument(name);
            default:
                throw new UnsupportedOperationException("Unsupported document type: " + type);
        }
    }
}

3. Паттерн Strategy (Стратегия)
3.1. Определение
Паттерн Strategy — это поведенческий паттерн, который определяет семейство алгоритмов, инкапсулирует каждый из них и делает их взаимозаменяемыми. Стратегия позволяет изменять алгоритм независимо от клиентов, которые его используют.

Структура:

Context — содержит ссылку на стратегию и делегирует ей выполнение.

Strategy — интерфейс, общий для всех стратегий.

ConcreteStrategy — конкретные реализации алгоритмов.

3.2. Особенности тестирования Strategy-паттернов
Ключевые аспекты тестирования:

Аспект	Описание
Тестирование каждой стратегии	Каждая реализация должна быть протестирована отдельно
Тестирование контекста	Проверка, что контекст правильно делегирует стратегии
Тестирование переключения стратегий	Проверка, что можно динамически менять стратегию
Тестирование комбинаций	Проверка стратегий в различных контекстах
Инварианты	Проверка, что стратегии не нарушают инварианты контекста
3.3. Пример: Тестирование паттерна Strategy
Код:

java
// Интерфейс стратегии
public interface SortStrategy {
    <T extends Comparable<T>> void sort(List<T> list);
}

// Конкретные стратегии
public class BubbleSortStrategy implements SortStrategy {
    @Override
    public <T extends Comparable<T>> void sort(List<T> list) {
        // Реализация пузырьковой сортировки
        int n = list.size();
        for (int i = 0; i < n - 1; i++) {
            for (int j = 0; j < n - i - 1; j++) {
                if (list.get(j).compareTo(list.get(j + 1)) > 0) {
                    Collections.swap(list, j, j + 1);
                }
            }
        }
    }
}

public class QuickSortStrategy implements SortStrategy {
    @Override
    public <T extends Comparable<T>> void sort(List<T> list) {
        // Реализация быстрой сортировки
        quickSort(list, 0, list.size() - 1);
    }
    
    private <T extends Comparable<T>> void quickSort(List<T> list, int low, int high) {
        if (low < high) {
            int pi = partition(list, low, high);
            quickSort(list, low, pi - 1);
            quickSort(list, pi + 1, high);
        }
    }
    // ... остальная реализация
}

// Контекст
public class Sorter {
    private SortStrategy strategy;
    
    public Sorter(SortStrategy strategy) {
        this.strategy = strategy;
    }
    
    public void setStrategy(SortStrategy strategy) {
        this.strategy = strategy;
    }
    
    public <T extends Comparable<T>> void sort(List<T> list) {
        if (list == null || list.isEmpty()) {
            throw new IllegalArgumentException("List cannot be null or empty");
        }
        strategy.sort(list);
    }
    
    public void validate(List<?> list) {
        // Проверка инвариантов
        if (list == null) {
            throw new IllegalArgumentException("List cannot be null");
        }
        // Инвариант: список не должен содержать null
        if (list.contains(null)) {
            throw new IllegalStateException("List contains null elements");
        }
    }
}

        assertEquals(Arrays.asList(1, 2, 3, 5, 8, 9), list);
    }
    
    @Test
    void testSorter_WithQuickSort() {
        Sorter sorter = new Sorter(new QuickSortStrategy());
        List<Integer> list = Arrays.asList(5, 3, 8, 1, 9, 2);

        assertEquals(Arrays.asList(1, 2, 3, 5, 8, 9), list);
    }
    
    // 3. Тестирование переключения стратегий
    @Test
    void testSorter_StrategySwitch() {
        Sorter sorter = new Sorter(new BubbleSortStrategy());

    @Test

        Sorter sorter = new Sorter(new QuickSortStrategy());

    // 6. Тестирование инвариантов
    @Test
    void testSorter_Invariants() {
        Sorter sorter = new Sorter(new QuickSortStrategy());

        // Проверка инвариантов до сортировки
        sorter.validate(list);
        
        sorter.sort(list);
        
        // Проверка инвариантов после сортировки
        sorter.validate(list);
    }
}
3.4. Комбинированное тестирование: Factory + Strategy
Часто паттерны Factory и Strategy используются вместе. Например, фабрика может создавать объект, а стратегия определяет его поведение.

Пример:

java
public interface PaymentStrategy {
    void pay(double amount);
}

public class CreditCardStrategy implements PaymentStrategy { ... }
public class PayPalStrategy implements PaymentStrategy { ... }

public class PaymentProcessor {
    private PaymentStrategy strategy;
    
    public PaymentProcessor(PaymentStrategy strategy) {
        this.strategy = strategy;
    }
    
    public void processPayment(double amount) {
        // Логика обработки
        strategy.pay(amount);
    }
}

public class PaymentFactory {
    public static PaymentStrategy createStrategy(String type, Map<String, String> params) {
        switch (type) {
            case "CREDIT_CARD":
                return new CreditCardStrategy(params.get("number"), params.get("cvv"));
            case "PAYPAL":
                return new PayPalStrategy(params.get("email"), params.get("password"));
            default:
                throw new UnsupportedOperationException("Unknown payment method");
        }
    }
}
Комбинированный тест:

java
@Test
void testPaymentFactoryAndStrategy() {
    // Создаём стратегию через фабрику
    Map<String, String> params = Map.of("number", "1234-5678-9012-3456", "cvv", "123");
    PaymentStrategy strategy = PaymentFactory.createStrategy("CREDIT_CARD", params);
    
    // Используем стратегию
    PaymentProcessor processor = new PaymentProcessor(strategy);
    processor.processPayment(100.00);
    
    // Проверка, что платёж обработан корректно
    assertTrue(processor.isPaymentProcessed());
    assertEquals(100.00, processor.getProcessedAmount());
}
4. Практические рекомендации по тестированию паттернов
4.1. Тестирование Factory
Проверяйте создание объектов всех типов — тестируйте фабрику на всех возможных типах.

Проверяйте обработку ошибок — тестируйте невалидные параметры.

Проверяйте состояние созданных объектов — убедитесь, что объекты создаются в корректном состоянии.

Тестируйте инварианты — проверяйте, что созданные объекты соблюдают инварианты.

Используйте контрактные тесты — для проверки всех реализаций.

Проверяйте побочные эффекты — фабрика не должна изменять внешнее состояние.

4.2. Тестирование Strategy
Тестируйте каждую стратегию отдельно — проверяйте корректность алгоритма.

Тестируйте контекст — проверяйте, что контекст правильно делегирует стратегию.

Тестируйте переключение стратегий — проверяйте динамическую смену алгоритмов.

Тестируйте с разными типами данных — стратегии должны работать корректно с разными данными.

Проверяйте инварианты — стратегия не должна нарушать инварианты контекста.

4.3. Общие рекомендации
Используйте тестовые фабрики для создания объектов в тестах.

Применяйте контрактное тестирование для проверки всех реализаций.

Используйте параметризованные тесты для проверки набора данных.

Внедряйте проверки инвариантов в тесты.

Тестируйте как успешные, так и ошибочные сценарии.

5. Итоговый вывод по лекции
Тестирование паттернов Factory и Strategy требует системного подхода, учитывающего как их структуру, так и динамическое поведение.

Ключевые тезисы для запоминания:

Factory-паттерны требуют проверки корректности создания объектов, обработки ошибок и состояния объектов.

Strategy-паттерны требуют проверки каждой стратегии отдельно, а также проверки контекста и переключения стратегий.

Контрактное тестирование эффективно для проверки всех реализаций паттернов.

Инварианты должны быть проверены как для создаваемых объектов, так и для контекстов.

Параметризованные тесты помогают уменьшить дублирование при тестировании разных стратегий и фабрик.

Комбинации паттернов (Factory + Strategy) требуют комплексного тестирования.
