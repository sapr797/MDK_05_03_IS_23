## 1. Введение: От поведения к логике

На предыдущих лекциях мы рассмотрели:
- **Pairwise Testing** — для комбинаций входных параметров.
- **MBT на основе FSM** — для последовательностей состояний.

Однако существует класс систем, где поведение определяется не столько последовательностью действий, сколько **сложной бизнес-логикой**, основанной на множестве условий. Классический пример — системы принятия решений, кредитные скоринги, правила расчета скидок, валидация сложных форм.

**Проблема:** Если в логике участвует **N** условий, полный перебор всех комбинаций условий даёт **2^N** (в случае бинарных условий) или **K^N** (для многозначных) вариантов.

**Решение:** Использовать **Таблицы решений (Decision Tables)** и **Блок-схемы (Flowcharts)** как формальные модели для генерации минимального, но покрывающего набора тестов.

## 2. Таблицы решений (Decision Tables)

### 2.1. Определение и структура

**Таблица решений** — это структурная форма представления бизнес-логики, которая связывает комбинации условий (входных данных) с действиями (выходными данными или результатами).

**Структура классической таблицы решений:**

| Компонент | Описание |
|-----------|----------|
| **Условия (Conditions)** | Набор логических выражений или атрибутов, которые могут принимать значения (истина/ложь или перечисление). |
| **Действия (Actions)** | Набор операций или результатов, которые выполняются при выполнении определенной комбинации условий. |
| **Правила (Rules)** | Столбцы, представляющие уникальные комбинации условий и соответствующие им действия. |
| **Таблица правил** | Матрица, где каждая строка — это условие или действие, а каждый столбец — это отдельное правило. |

### 2.2. Пример 1: Простая таблица решений

**Бизнес-сценарий:** Интернет-магазин предоставляет скидку.

**Условия:**
1. Сумма заказа > 5000 ₽ (да/нет)
2. Клиент является постоянным (да/нет)

**Действия:**
- Скидка 10%
- Скидка 5%
- Скидка не предоставляется

**Таблица решений:**

| Условия/Правила | Правило 1 | Правило 2 | Правило 3 | Правило 4 |
|-----------------|-----------|-----------|-----------|-----------|
| Сумма > 5000    | Да        | Да        | Нет       | Нет       |
| Постоянный      | Да        | Нет       | Да        | Нет       |
| **Действия**    |           |           |           |           |
| Скидка 10%      | **X**     |           |           |           |
| Скидка 5%       |           | **X**     | **X**     |           |
| Нет скидки      |           |           |           | **X**     |

**Анализ:**
- **Правило 1:** Сумма > 5000 + Постоянный → 10% скидка.
- **Правило 2:** Сумма > 5000 + Не постоянный → 5% скидка.
- **Правило 3:** Сумма ≤ 5000 + Постоянный → 5% скидка (лояльность).
- **Правило 4:** Сумма ≤ 5000 + Не постоянный → скидки нет.

**Тест-кейсы:** На основе таблицы генерируется 4 тест-кейса (по одному на каждое правило).

---

### 2.3. Пример 2: Таблица решений с многозначными условиями

**Бизнес-сценарий:** Расчет страхового взноса.

**Условия:**
1. Возраст: (< 25 лет, 25–45 лет, > 45 лет)
2. Стаж вождения: (< 2 лет, 2–10 лет, > 10 лет)
3. Наличие страховых случаев в прошлом году: (0, 1, > 1)

**Таблица решений (фрагмент):**

| Условия/Правила   | Пр.1 | Пр.2 | Пр.3 | Пр.4 | Пр.5 |
|-------------------|------|------|------|------|------|
| Возраст           | <25  | <25  | 25-45| 25-45| >45  |
| Стаж вождения     | <2   | 2-10 | <2   | >10  | >10  |
| Страховые случаи  | 0    | 0    | 0    | 0    | 1    |
| **Действия**      |      |      |      |      |      |
| Коэффициент (X)   | 2.0  | 1.5  | 1.5  | 1.0  | 1.2  |
| Дополнительная проверка | Да | Нет | Нет | Нет | Да |

**Важно:** Полная таблица будет содержать 3 * 3 * 3 = 27 правил. Оптимизация достигается за счёт **свёртки правил** (объединения правил с одинаковыми действиями).

---

### 2.4. Свёртка правил (Rule Collapsing)

**Цель:** Уменьшить количество правил за счет группировки.

**Правило:** Если два правила отличаются только по одному условию, но приводят к одинаковым действиям, их можно объединить, заменив различающееся условие на "не важно" (don't care, обозначается `-`).

**Пример свертки:**

| | Правило 1 | Правило 2 | Свёрнутое правило |
|---|-----------|-----------|-------------------|
| Сумма > 5000 | Да | Нет | - |
| Постоянный | Да | Да | Да |
| **Скидка** | **5%** | **5%** | **5%** |

*Пояснение:* Если скидка 5% предоставляется и при сумме > 5000, и при сумме ≤ 5000, лишь бы клиент был постоянным, то условие "Сумма > 5000" становится неважным.

---

### 2.5. Алгоритм генерации тестов из таблицы решений

1. **Определение условий:** Выделить все входные параметры, влияющие на бизнес-правило.
2. **Определение действий:** Выделить все выходные результаты или выполняемые операции.
3. **Определение значений:** Для каждого условия определить множество допустимых значений.
4. **Построение полной таблицы:** Сгенерировать все возможные комбинации условий (декартово произведение).
5. **Заполнение действий:** Для каждой комбинации определить ожидаемые действия.
6. **Свёртка правил:** Объединить правила с одинаковыми действиями.
7. **Генерация тест-кейсов:** Каждое правило (столбец) превращается в отдельный тест-кейс.

## 3. Блок-схемы (Flowcharts) как модели

### 3.1. Определение и структура

**Блок-схема** — это графическое представление алгоритма или процесса, где каждый этап (действие, проверка условия, ввод/вывод) отображается в виде блока, а связи между ними — в виде стрелок (потоков управления).

**Основные элементы блок-схем:**

| Символ | Название | Описание |
|--------|----------|----------|
| ○ | Терминатор | Начало или конец алгоритма. |
| ◇ | Условие (Ромб) | Логическое ветвление (да/нет). |
| ▭ | Процесс (Прямоугольник) | Выполнение операции или действия. |
| ║ | Параллельный процесс | Выполнение нескольких операций одновременно. |
| —> | Стрелка | Направление потока управления. |

### 3.2. Блок-схема как модель для тестирования

Блок-схема, по сути, является **графом потока управления (Control Flow Graph)**. Тестирование на основе блок-схем позволяет генерировать тесты для покрытия:

1. **Всех операторов** (Statement Coverage) — простейший критерий.
2. **Всех ветвей** (Branch Coverage) — проверка всех условий.
3. **Всех путей** (Path Coverage) — проверка всех маршрутов через алгоритм.

### 3.4. Генерация тестов из блок-схемы

**Метод:** Проход по графу.

**Тест-кейсы (на основе покрытия ветвей):**

| ID | Путь в блок-схеме | Покрываемые ветви |
|----|-------------------|-------------------|
| TC-01 | Начало → Товар есть → Расчет → Баланс достаточен → Списание → Оформление → Конец | Да, Да |
| TC-02 | Начало → Товар есть → Расчет → Баланс недостаточен → Предложение альтернативы → Конец | Да, Нет |
| TC-03 | Начало → Товара нет → Уведомление → Конец | Нет |

**Критерий покрытия путей:** Если в блок-схеме есть циклы (например, повторный ввод данных), количество путей становится бесконечным. В таких случаях используют ограничение длины пути или применяют алгоритмы поиска циклов.

---

### 3.5. Блок-схемы vs Таблицы решений

| Характеристика | Таблицы решений | Блок-схемы |
|----------------|-----------------|------------|
| **Основное применение** | Бизнес-правила, сложная логика | Алгоритмы, процессы, потоки управления |
| **Учёт последовательности** | Нет (только комбинации условий) | Да (ветвления и циклы) |
| **Наглядность** | Компактная, легко анализировать пропуски | Наглядная, но сложная для больших систем |
| **Масштабируемость** | Высокая (свёртка правил) | Ограниченная (разрастается граф) |
| **Тип покрытия** | Покрытие правил (все комбинации) | Покрытие ветвей/путей |

## 4. Совместное применение: Таблицы решений + Блок-схемы

На практике эти две модели часто используются совместно:

1. **Блок-схема** описывает *общий поток* выполнения (какой блок за каким идёт).
2. **Таблица решений** описывает *сложную логику* внутри отдельных блоков (например, внутри блока "Расчет стоимости" может быть таблица решений со множеством условий).

**Пример:** Система кредитного скоринга.
- **Блок-схема:** Общий процесс (подача заявки → проверка данных → расчет скоринга → принятие решения).
- **Таблица решений:** Внутри блока "Расчет скоринга" — таблица, определяющая коэффициент на основе возраста, дохода, кредитной истории и т.д.

## 5. Генерация тестов: Практический алгоритм

### 5.1. Пошаговая инструкция

**Шаг 1: Формализация требований.**
- Преобразовать текстовые требования в структурированную модель.
- Если логика ветвится → блок-схема.
- Если логика множественная и комбинаторная → таблица решений.

**Шаг 2: Определение условий и действий.**
- Для таблицы решений: выписать все условия и действия.
- Для блок-схемы: выделить все узлы и переходы.

**Шаг 3: Построение модели.**
- Создать таблицу/схему вручную или с использованием инструментов.

**Шаг 4: Оптимизация.**
- Свернуть таблицу решений (убрать незначащие правила).
- Упростить блок-схему (убрать недостижимые узлы).

**Шаг 5: Генерация тестов.**
- Каждое правило таблицы решений → тест-кейс.
- Каждый путь/ветвь в блок-схеме → тест-кейс.

**Шаг 6: Документирование.**
- Записать в виде формальных тест-кейсов с предусловиями, шагами и ожидаемыми результатами.

7. Сравнение техник: Когда что использовать
Ситуация	Рекомендуемая техника
Много независимых условий, результат зависит от их комбинации	Таблица решений
Алгоритм с ветвлениями и циклами	Блок-схема + покрытие путей

10. Итоговый вывод по лекции
Таблицы решений и блок-схемы являются мощными инструментами тест-дизайна, которые позволяют:

Визуализировать сложную логику и сделать её понятной для всех участников команды.

Сократить количество тестов за счет свёртки правил и устранения избыточности.

Обеспечить полноту покрытия всей бизнес-логики.

Автоматизировать генерацию тест-кейсов на основе формальных моделей.

Ключевые тезисы для запоминания:

Таблицы решений оптимальны для комбинаторной логики (много условий, которые вместе определяют результат).

Блок-схемы оптимальны для алгоритмической логики (последовательность шагов, ветвления, циклы).

На практике эти техники дополняют друг друга — блок-схема описывает процесс, а таблицы решений — сложные узлы.

Главная ценность этих техник в том, что они превращают неформальные требования в формальную модель, которую можно верифицировать и из которой можно автоматически генерировать тесты.
