## 1. Введение в Model-Based Testing (MBT)

### 1.1. Проблематика традиционного подхода

В предыдущих лекциях мы рассматривали техники, основанные на статическом наборе входных данных (эквивалентность, граничные значения, попарное тестирование). Однако многие современные системы являются **динамическими** — их поведение зависит не только от текущих входных данных, но и от **истории взаимодействия** (состояния системы).

**Пример проблемы:**
> Интернет-магазин. Корзина покупок.
> - Действие "Добавить товар" работает по-разному в зависимости от того, пустая корзина или нет.
> - Действие "Применить купон" работает только если корзина не пуста.
> - Действие "Оформить заказ" доступно только после заполнения всех полей.

Просто перебрать все комбинации входных данных здесь недостаточно — нужно учитывать **последовательность действий** и **состояния**, в которых оказывается система.

### 1.2. Определение MBT

**Model-Based Testing (MBT)** — это техника тест-дизайна, при которой тестовые сценарии автоматически или полуавтоматически генерируются из формальной модели поведения системы.

**Ключевая идея:** Вместо того чтобы вручную писать сотни тест-кейсов, мы создаём **компактную математическую модель** системы, а затем с помощью инструментов разворачиваем её в бесконечное множество тестовых путей.

### 1.3. Основные преимущества MBT

| Преимущество | Описание |
|--------------|----------|
| **Автоматизация генерации** | Тесты создаются автоматически из модели, экономия времени на рутинной работе. |
| **Полнота покрытия** | Можно гарантировать покрытие всех состояний или всех переходов. |
| **Раннее обнаружение дефектов** | Модель выявляет логические ошибки ещё на этапе проектирования. |
| **Живая документация** | Модель служит актуальной документацией по поведению системы. |

### 1.4. Недостатки и ограничения

| Недостаток | Описание |
|------------|----------|
| **Сложность создания моделей** | Требует высокой квалификации и времени на начальном этапе. |
| **Проблема масштабирования** | Для сложных систем модель может стать такой же сложной, как и сама система. |
| **Оркестрация** | Сложно синхронизировать модель с постоянно меняющимся кодом (подходит для Agile с трудом). |

## 2. Конечные автоматы (Finite State Machines — FSM) как основа MBT

### 2.1. Определение и компоненты

**Конечный автомат (FSM)** — это математическая модель, описывающая систему с конечным числом состояний и правилами перехода между ними под воздействием внешних событий.

**Компоненты FSM:**
1. **Q** — конечное множество состояний (States).
2. **Σ** — конечное множество входных символов/событий (Events/Inputs).
3. **δ** — функция переходов: Q × Σ → Q (Transition Function).
4. **q₀** — начальное состояние (Initial State).
5. **F** — множество финальных/принимающих состояний (Final States) — опционально.

### 2.2. Графическое представление

Конечный автомат обычно изображается в виде **ориентированного графа**:
- **Вершины** (круги/прямоугольники) — состояния системы.
- **Дуги** (стрелки) — переходы, подписанные событиями/действиями.

### 2.3. Простой пример: Автомат двери

Рассмотрим систему "Электронная дверь" с замком.

**Состояния:**
- `Closed` — дверь закрыта и заперта.
- `Open` — дверь открыта.
- `Locked` — дверь заблокирована.

**События:**
- `unlock` — отпирание.
- `open` — открытие.
- `close` — закрытие.
- `lock` — запирание.

**Диаграмма переходов:**
[Closed] --unlock--> [Open]
[Open] --close--> [Closed]
[Closed] --lock--> [Locked]
[Locked] --unlock--> [Closed]

text

*Примечание:* Переходы, не описанные в модели, считаются невозможными или некорректными (например, попытка открыть заблокированную дверь).

## 3. Типы моделей в MBT

### 3.1. Детерминированные и недетерминированные автоматы

| Тип | Описание | Пример |
|-----|----------|--------|
| **Детерминированный (DFA)** | Для каждого состояния и события существует не более одного перехода. Легко тестировать. | Банкомат: ввод PIN-кода всегда приводит к одному результату. |
| **Недетерминированный (NFA)** | Из одного состояния по одному событию возможны несколько переходов. Используется для моделирования неполной спецификации. | Система рекомендаций: одно действие пользователя может привести к разным результатам. |

### 3.2. Автоматы Мура и Мили (Moore vs Mealy)

| Характеристика | Автомат Мура | Автомат Мили |
|----------------|--------------|--------------|
| **Выходные сигналы** | Зависят только от состояния. | Зависят от состояния И от входного события. |
| **Визуализация** | Выход подписан внутри вершины. | Выход подписан на дуге перехода. |
| **Применение** | Системы, где состояние определяет поведение (например, статус заказа). | Системы, где результат действия зависит от контекста (например, валидация формы). |

## 4. Стратегии генерации тестов из FSM

### 4.1. Покрытие всех состояний (State Coverage)

Каждое состояние модели должно быть посещено хотя бы одним тестом.

**Цель:** Проверить, что все состояния достижимы и корректно обрабатываются.

**Пример:** Для автомата двери нужно посетить состояния `Closed`, `Open`, `Locked`.

**Недостаток:** Не проверяет переходы между состояниями.

---

### 4.2. Покрытие всех переходов (Transition Coverage)

Каждый переход в модели должен быть выполнен хотя бы одним тестом.

**Цель:** Проверить все возможные реакции системы на события.

**Пример:** Для автомата двери нужно проверить переходы:
- `Closed --unlock--> Open`
- `Open --close--> Closed`
- `Closed --lock--> Locked`
- `Locked --unlock--> Closed`

**Минимальное количество тестов:** Один тестовый сценарий может покрыть несколько переходов (например, `Locked --unlock--> Closed --unlock--> Open`).

---

### 4.3. Покрытие всех путей (Path Coverage)

Покрытие всех возможных маршрутов в графе состояний.

**Цель:** Проверить все сценарии взаимодействия с системой.

**Проблема:** В графах с циклами количество путей бесконечно. Обычно ограничиваются путями определённой длины или используют эвристики.

---

### 4.4. Критерий "Китайский ресторан" (Chinese Postman) и другие оптимизации

Используются алгоритмы теории графов для нахождения минимального набора тестов, покрывающего все переходы (похоже на задачу маршрута почтальона).

## 5. Расширенные модели

### 5.1. Statecharts (Диаграммы состояний UML)

**Statecharts** — это расширение классических FSM, поддерживающее:
- **Иерархию состояний** (суперсостояния и подсостояния).
- **Параллельные состояния** (ор-состояния).
- **Исторические состояния** (возврат в последнее подсостояние).

**Пример:** Система управления проектом может находиться в состоянии `Активен`, внутри которого может быть `В работе`, `На ревью`, `Готово`.

### 5.2. Событийно-ориентированные модели

Вместо явного задания состояний, модель описывается через поток событий и реакций на них. Подходит для асинхронных систем.

### 5.3. Модели потоков данных

Описывают, как данные преобразуются и передаются между компонентами системы. Используется для тестирования ETL-процессов и интеграционных потоков.

## 6. Инструменты для MBT

| Инструмент | Описание | Особенности |
|------------|----------|-------------|
| **GraphWalker** | Open-source фреймворк для MBT. | Поддерживает FSM, Statecharts. Генерация тестов на Java, Python, JS. |
| **Spec Explorer** (Microsoft) | Инструмент для моделирования поведения систем. | Основан на C# и работе с конечными автоматами. |
| **Conformiq Designer** | Коммерческий инструмент для автоматической генерации тестов. | Интегрируется с HP ALM, Jira. |
| **Tcases** | Open-source инструмент для генерации тестов из моделей. | Поддерживает комбинаторное тестирование и сценарии. |
| **RapiCover** | Инструмент для анализа покрытия модели. | Позволяет оценить полноту тестирования. |

## 7. Жизненный цикл MBT в проекте

```mermaid
graph TD
    A[Анализ требований] --> B[Построение модели поведения]
    B --> C[Верификация модели]
    C --> D[Генерация тестовых сценариев]
    D --> E[Выполнение тестов]
    E --> F[Анализ покрытия модели]
    F --> G{Достигнуто ли покрытие?}
    G -->|Нет| D
    G -->|Да| H[Формирование отчета]
Пояснение этапов:

Анализ требований: Изучение документации, выделение ключевых состояний и событий.

Построение модели: Создание FSM/Statechart вручную или с использованием инструментов.

Верификация модели: Проверка, что модель соответствует требованиям и не содержит противоречий.

Генерация тестов: Автоматическое создание тестовых сценариев по выбранному критерию покрытия.

Выполнение тестов: Ручное или автоматизированное выполнение.

Анализ покрытия: Проверка, какие части модели остались непокрытыми.

Итерация: При необходимости — доработка модели и повторная генерация.

8. Сравнение MBT с традиционными техниками
Критерий	Традиционные техники (Pairwise, EQP)	MBT (FSM)
Объект тестирования	Отдельные входные параметры	Поведение системы во времени
Учёт последовательности	Нет	Да
Покрытие	Комбинации значений	Состояния и переходы
Сложность внедрения	Низкая	Высокая
Поддержка изменений	Низкая (ручной пересмотр)	Высокая (обновление модели)
Автоматизация генерации	Частичная (PICT)	Полная (GraphWalker и др.)
9. Практический пример: Тестирование интернет-магазина с помощью FSM
9.1. Исходные данные
Тестируем процесс оформления заказа.

Состояния системы:

CART_EMPTY — корзина пуста.

CART_FILLED — товары добавлены.

ADDRESS_FILLED — адрес доставки указан.

PAYMENT_SELECTED — способ оплаты выбран.

ORDER_CONFIRMED — заказ подтверждён.

События:

addItem() — добавить товар.

fillAddress() — заполнить адрес.

selectPayment() — выбрать оплату.

confirmOrder() — подтвердить заказ.

clearCart() — очистить корзину.

9.2. Модель переходов
text
[CART_EMPTY] --addItem--> [CART_FILLED]
[CART_FILLED] --addItem--> [CART_FILLED] (самопереход)
[CART_FILLED] --clearCart--> [CART_EMPTY]
[CART_FILLED] --fillAddress--> [ADDRESS_FILLED]
[ADDRESS_FILLED] --fillAddress--> [ADDRESS_FILLED]
[ADDRESS_FILLED] --selectPayment--> [PAYMENT_SELECTED]
[PAYMENT_SELECTED] --selectPayment--> [PAYMENT_SELECTED]
[PAYMENT_SELECTED] --confirmOrder--> [ORDER_CONFIRMED]
[ORDER_CONFIRMED] -- (финальное состояние)
9.3. Генерация тестов по критерию "Покрытие всех переходов"
Тест-кейс	Действия	Ожидаемый результат
TC-01	addItem()	Переход в CART_FILLED
TC-02	clearCart() из CART_FILLED	Переход в CART_EMPTY
TC-03	fillAddress() из CART_FILLED	Переход в ADDRESS_FILLED
TC-04	selectPayment() из ADDRESS_FILLED	Переход в PAYMENT_SELECTED
TC-05	confirmOrder() из PAYMENT_SELECTED	Переход в ORDER_CONFIRMED
TC-06	addItem() в CART_FILLED	Остаться в CART_FILLED
Итог: 6 тестов вместо попытки перебрать все возможные комбинации действий пользователя.

10. Метрики и оценка качества тестирования при MBT
Метрика	Формула	Значение
State Coverage	(Посещённые состояния / Общее число состояний) * 100%	Показывает, сколько состояний было проверено.
Transition Coverage	(Выполненные переходы / Общее число переходов) * 100%	Основной показатель для FSM.
Depth Coverage	Максимальная длина пути в модели	Показывает, насколько глубокие сценарии проверены.
Requirements Coverage	(Покрытые требования / Все требования) * 100%	Связь модели с бизнес-требованиями.
11. Итоговый вывод по лекции
Model-Based Testing с использованием конечных автоматов — это переход от реактивного тестирования к проактивному. Вместо того чтобы гадать, какие сценарии могут сломать систему, мы формализуем её поведение и автоматически генерируем все критически важные пути.

Ключевые тезисы для запоминания:

MBT позволяет тестировать не отдельные значения, а поведение системы во времени.

FSM — базовая модель, описывающая состояния и переходы.

Покрытие переходов — основной критерий качества в MBT.

Инструменты (GraphWalker, Spec Explorer) делают генерацию тестов полностью автоматической.

MBT особенно эффективен для систем с большим количеством состояний (CRM, ERP, банковские системы).

Задание на семинар
Задание: Построить конечный автомат для системы управления задачами (Todo-лист) и сгенерировать тесты.

Состояния задачи:

NEW — новая задача.

IN_PROGRESS — в работе.

REVIEW — на проверке.

DONE — выполнена.

События:

start() — начать работу.

complete() — завершить работу (отправить на проверку).

approve() — одобрить задачу.

reject() — отклонить задачу (вернуть в работу).

Задания для студентов:

Нарисовать диаграмму переходов (можно вручную или используя PlantUML).

Определить, какие переходы недопустимы (например, из NEW сразу в DONE без start).

Сгенерировать набор тестов для покрытия всех переходов.

Посчитать, сколько тестов потребуется для покрытия всех путей длиной до 3 шагов.
